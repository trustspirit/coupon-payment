## 1. 사용자가 말한 시나리오 (원문 요지)

1. 사용자가 특정 아이템에 쿠폰을 적용해 구매한다
2. 아이템 재고(stock)가 줄어든다
3. 쿠폰이 사용 처리되어 더 이상 쓸 수 없게 된다
4. 결제가 진행되고, 완료되면 사용자에게 **구매 완료**가 결과로 전달된다
5. **구매 취소** 시 쿠폰과 아이템 재고가 원상태로 돌아오고 결제도 취소된다
6. 사용자의 가설: "이때는 Kafka나 SQS가 필요할 수도 있을 듯"

---

## 2. 이미 보이는 핵심 학습 주제 (Claude 메모)

- **여러 자원의 일관성**: 재고, 쿠폰 상태, 주문, 결제를 하나의 결과로 맞추기
- **외부 시스템(PG)은 DB 트랜잭션에 묶을 수 없다** → Saga 패턴(보상 트랜잭션)
  - Orchestration(주문 서비스가 지휘) vs Choreography(이벤트로 각자 반응) 비교
- **상태 머신**
  - 주문: `CREATED → PAYMENT_PENDING → PAID → CANCELLED` (+ `PAYMENT_FAILED`, `EXPIRED`)
  - 쿠폰: `ISSUED → RESERVED → USED → (취소 시) ISSUED`
- **선점(예약) vs 즉시 차감**: 결제 전에 재고와 쿠폰을 "예약"하고, 결제가 안 되면 일정 시간 뒤 자동 해제
- **진짜 `Idempotency-Key`가 필요해지는 지점**: 결제 요청 재시도, PG 웹훅 중복 수신
- **Transactional Outbox**: "주문 상태 변경 커밋"과 "이벤트 발행"을 원자적으로 연결
- **멱등 consumer, 재시도, DLT(Dead Letter Topic)**
- 동시성: 같은 쿠폰을 두 주문에 동시에 적용하는 경우(낙관적 락 `@Version` 후보), 인기 아이템 재고 경쟁(쿠폰 프로젝트 단계 2 기법 재사용)

## 3. Kafka / SQS가 필요한가? (가설 검증 포인트)

쿠폰 프로젝트에서 배운 기준("소비자가 여럿이거나, 다른 서비스이거나, 유실되면 안 되고 재처리가 필요할 때")으로 따져볼 것:

- 단일 서버(모놀리스)라면 재고, 쿠폰, 주문 변경은 **로컬 트랜잭션 하나**로 묶을 수 있다. 메시지 큐가 필요한 곳은 **결제(외부)와의 경계**다.
- PG가 결과를 **비동기 웹훅**으로 준다면 → 결과 수신 후 처리를 큐로 분리할 이유가 생긴다.
- 주문, 재고, 쿠폰, 결제를 **별도 서비스**로 나눈다면 → Saga 메시징이 필수가 된다(Kafka가 자연스러움).
- 결제 대기 만료(예: 10분 뒤 자동 취소) → 지연 큐(SQS delay queue) vs 스케줄러 비교.

## 4. 다음 브레인스토밍에서 답해야 할 열린 질문

1. 주문, 재고, 쿠폰, 결제를 하나의 Spring 앱에서 할까, 서비스를 나눌까? (Kafka 필요성이 여기서 갈림)
2. 사용자는 결제 결과를 **즉시** 받아야 하나, "결제 처리 중" 뒤에 나중에 받아도 되나?
3. PG는 어떻게 흉내 낼까? (가짜 PG 서버: 지연, 실패, 타임아웃, 중복 웹훅 주입)
4. 결제 대기 중 재고와 쿠폰 예약은 얼마 동안 유지하나? 만료 처리는?
5. 주문 1건에 아이템 여러 개? 부분 취소?
6. 쿠폰 할인 방식: 정액 / 정률 / 최소 주문 금액?
7. "결제는 성공했는데 우리 쪽 처리가 실패" 같은 불일치는 어떻게 수습할까? (자동 환불? 재시도?)
8. 취소 가능 조건: 결제 완료 후 언제까지? 이미 만료된 쿠폰을 원복하면?
